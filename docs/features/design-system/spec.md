# 명세: LexWatch 디자인 시스템

- 상태: 검토 반영본 v2 (2026-11-19). 변경: DS-02 글자 크기 구분, DS-09와 DS-10 구체화, DS-12 제외, 백엔드 범위 포함, DS-15 크기
- 작성: hh.jang
- 근거 자료: [research.md](research.md), [설계 문서 5.3절](../../superpowers/specs/2026-11-16-lexwatch-design.md)

## 1. 해결할 문제

LexWatch 화면에는 디자인 토큰도 공용 컴포넌트도 없다. 화면마다 Tailwind 기본 색을 그때그때 골라 쓴다. 그 결과 아래 문제가 생겼다.

1. `globals.css`의 레이어 밖 `body` 규칙이 Tailwind 클래스를 덮어쓴다. 배경 `bg-slate-50`이 적용되지 않고, 다크 모드 시스템에서는 흰 카드 위에 흰 글씨가 나온다. 한글은 Arial 대신 운영체제 기본 글꼴로 바뀌어 맥과 윈도우에서 다르게 보인다.
2. 같은 색이 서로 다른 뜻으로 쓰인다. 초록은 NVIDIA 출처, 단계 성공, 승인 버튼, 신조문 배경에 모두 쓰인다. 그래서 출처 라벨이 품질 판정처럼 읽힌다. 이 제품은 "정직성 배지"를 원칙으로 내세우므로 이 혼동은 제품 메시지를 해친다.
3. `ClosedIrrelevant`, `Succeeded`, `finance` 같은 영어 상태값이 한국어 화면에 그대로 나온다.
4. 버튼 스타일이 열 가지 안팎이고, 포커스 표시가 한 곳도 없다.
5. 신구조문 비교가 바뀐 부분을 표시하지 않는다. 휴대폰에서도 두 칸으로 나뉜다.
6. 승인 대기함의 한 행에 정보 일곱 개가 같은 무게로 놓여, 크리틱 적발 여부를 훑어보기 어렵다.

## 2. 사용자

로펌 직원이다. 실제 사용자는 세 부류로 본다.

| 사용자 | 하는 일 | 화면에서 필요한 것 |
|---|---|---|
| 변호사(실무그룹 담당) | 초안을 읽고 승인, 수정, 반려 | 근거를 바로 열어 보기, 바뀐 조문 한눈에 보기, 실수로 승인하지 않기 |
| 패러리걸, 지식관리 담당 | 대기 목록을 정리하고 근거를 대조 | 많은 행을 빠르게 훑기, 키보드로 이동 |
| 관리자(운영) | 실패한 실행을 확인하고 재실행 | 단계별 상태와 오류를 한국어로 읽기 |

공통 조건: 긴 법령 문장을 오래 읽는다. 업무용 데스크톱이 주 환경이고 휴대폰은 확인용이다.

## 3. 범위

포함:
- 디자인 토큰(색, 글꼴, 간격, 모서리, 그림자, 움직임)과 대비 검사
- 공용 컴포넌트와 그 상태(기본, 마우스 올림, 포커스, 누름, 비활성, 로딩)
- 다섯 화면(승인 대기함, 검토 상세, 실행 이력, 실행 타임라인, 알림함)에 적용
- 앱 안의 디자인 시스템 문서 화면
- 백엔드: 법제처 공식 변경 표시(`<P>`) 보존과 검토 API의 근거 본문 앞부분(작성자 결정, 2026-11-19)
- Codex로 만든 3D 마스코트 "렉스"와 로고, 파비콘

하지 않을 것:
- 다크 모드. 이번에는 밝은 화면만 지원하고 `color-scheme: light`로 고정한다. 토큰은 나중에 다크 값을 넣을 수 있게 의미 이름으로 만든다.
- 로그인, 권한 체계 변경.
- Figma 파일 제작.

## 4. 요구사항

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| DS-01 | 전역 스타일이 Tailwind 클래스를 덮어쓰지 않는다 | 다크 모드 운영체제에서도 카드 글자색이 본문색이고 배경이 `canvas` 토큰 색이다. `globals.css`에 레이어 밖 색, 글꼴 규칙이 없다 |
| DS-02 | 한글 글꼴을 모든 환경에서 같게 보여 준다 | Pretendard Variable을 자체 호스팅으로 불러온다. 읽는 글(초안 문장, 조문, 알림 본문)은 16px, 줄높이 1.6 이상, 자간 0. 목록과 버튼 같은 UI 글자는 15px 이하를 허용한다. 숫자 열(신뢰도, 건수, 시간)은 고정폭 숫자 |
| DS-03 | 상태 색과 출처 색을 분리한다 | 출처 라벨(NVIDIA, 대체 구현, 재현)은 초록, 빨강, 주황, 노랑을 쓰지 않는다. 각 라벨에 글자와 아이콘이 함께 있다 |
| DS-04 | 모든 글자와 UI 경계가 WCAG 2.2 AA 대비를 만족한다 | 자동 테스트가 토큰 쌍(글자/배경, 경계/배경)의 대비를 계산해 글자 4.5:1, UI 경계 3:1 미만이면 실패한다 |
| DS-05 | 화면에 영어 상태값이 나오지 않는다 | 실행 상태, 그룹 검토 상태, 단계 상태, 알림 상태, 실무그룹 코드가 한국어 라벨로 나온다. 모르는 값은 원문을 회색으로 보여 준다(정보를 숨기지 않음) |
| DS-06 | 공용 컴포넌트로 같은 모양을 한 곳에서 관리한다 | Button, Badge(개수), StatusLozenge(상태), SourceLabel(출처), Card, Callout, Tooltip, Popover, Dialog를 공용 컴포넌트로 두고 화면 코드에서 직접 색 클래스를 쓰지 않는다 |
| DS-07 | 키보드만으로 모든 동작을 할 수 있다 | 모든 대화형 요소에 보이는 포커스 링(3:1 이상)이 있다. 대화상자는 포커스를 가두고 Esc로 닫힌다 |
| DS-08 | 신구조문의 바뀐 부분을 보여 준다 | 구조문의 삭제 부분은 `<del>`과 취소선, 신조문의 추가 부분은 `<ins>`와 밑줄로 표시하고 화면 읽기 프로그램용 숨김 텍스트를 붙인다. 768px 미만에서는 구조문과 신조문을 탭으로 바꿔 본다 |
| DS-09 | 인용 근거를 화면을 떠나지 않고 확인한다 | 초안의 인용 칩을 누르거나 Enter를 누르면 근거 제목과 본문 앞부분(API의 `excerpt`, 최대 240자)이 팝오버로 뜬다. 원문 링크가 있으면 팝오버 안에 둔다. Esc로 닫히고 포커스가 칩으로 돌아온다 |
| DS-10 | 승인을 실수로 하지 않는다 | 승인과 수정 후 승인 전에 확인 대화상자가 뜨고 무엇이 일어나는지(어느 그룹 알림함으로 발송, 되돌릴 수 없음) 적혀 있다. 반려는 지금처럼 사유 입력 뒤 확정하는 두 단계다. 결과와 오류는 화면 위 안내 상자로 알리고 화면 읽기 프로그램이 읽는다 |
| DS-11 | 승인 대기함을 빠르게 훑는다 | 크리틱 적발이 있는 행은 적발 수가 빨간 개수 배지로 앞에 나온다. 신뢰도는 숫자와 막대로 보인다 |
| DS-12 | (제외) | 검토 결과 이번 범위에서 뺐다. 지금은 버튼으로만 보내 한글 조합 중 전송 문제가 없다. design.md 1.2절 |
| DS-13 | 디자인 시스템을 앱 안에서 볼 수 있다 | `/design-system` 화면에 토큰(색 견본과 대비 값), 글꼴 척도, 컴포넌트와 상태 예시가 있다 |
| DS-14 | 제품 정체성을 보여 주는 에셋이 있다 | 로고 마크와 파비콘을 마스코트 얼굴로 만든다. 모든 에셋은 Codex 이미지 생성으로 만들고 생성 프롬프트를 저장소에 남긴다 |
| DS-15 | 3D 마스코트 "렉스"가 여유 있는 순간에 등장한다 | 남색 재킷과 저울 배지를 단 3D 클레이 부엉이. 기본형 1종과 상황 4종(승인 대기 없음, 알림 없음, 서버 깨우는 중, 불러오기 실패)을 쓴다. 빈 화면, 대기 화면, 오류 화면, 헤더 로고에만 나오고 **승인, 반려, 확인 대화상자, 초안 본문, 신구조문 옆에는 나오지 않는다.** 장식 이미지라 `alt=""`이고 같은 내용을 글로도 적는다. 투명 배경 WebP, 화면에 쓰는 크기의 2배 이상 해상도(헤더 32px, 빈 화면 180px), 장당 120KB 이하 |

## 5. 오류와 예외 상황

- 신구조문 한쪽이 비어 있으면(신설 조문, 삭제 조문) 하이라이트 없이 "신설" 또는 "삭제" 상태를 보여 준다.
- 비교할 글이 길어 계산이 오래 걸리면(조문 하나에 수천 자) 하이라이트를 포기하고 원문만 보여 준다. 화면이 멈추면 안 된다.
- 공식 변경 표시가 없는 실행(배포 전 수집분, 재현 데이터)은 화면에서 비교하고 "화면에서 비교"라고 밝힌다.
- 인용 ID에 해당하는 근거가 없으면 팝오버에 "근거를 찾을 수 없어요"를 보여 주고 칩은 경고 모양이 된다. 크리틱 1단과 같은 판단이다.
- 글꼴 파일을 못 불러오면 시스템 산세리프로 대체되고 레이아웃이 깨지지 않는다.
- 상태값 표에 없는 새 값이 오면 원문 그대로 중립 색으로 보여 준다.

## 6. 성공 판단

- 위 수용 기준을 자동 테스트(대비, 상태 라벨, 신구 대조 계산)와 화면 확인으로 검증한다.
- 기존 웹 테스트 27건과 타입 검사, 린트, 빌드가 계속 통과한다.

## 7. 배포 화면 진단 후 개선 (2026-11-19)

사용자 요청: 배포된 서비스와 디자인 시스템을 진단한 결과에 따라 복구하고 개선한다.
기존 밝은 화면, Pretendard, 남색 브랜드, 근거 확인과 승인 정책을 유지한다.

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| DS-16 | 실제 배포 CSS가 디자인 토큰과 일치한다 | 빌드 완료 후 최종 CSS에서 브랜드, 본문, 경고, 표면, 제목, 포커스 스타일과 밝은 모드 규칙을 검사한다. 기존 다크 모드 body 규칙이나 필수 스타일 누락이면 빌드가 실패한다. 캐시 없는 빌드와 반복 빌드 모두 통과한다. 공개 주소에서도 같은 검사를 실행할 수 있다 |
| DS-17 | 분류 점수를 초안 정확도로 오해하지 않는다 | `confidence`의 표시는 모두 ‘그룹 관련성’. 목록 상단과 디자인 시스템에 초안 정확도가 아니라는 설명. null은 —, 0과 1은 0%와 100% |
| DS-18 | 검토할 문제와 근거를 먼저 찾는다 | 초안의 지적 문장 수를 상세 상단에 표시하고 첫 지적 문장으로 이동한다. 지적이 없으면 자동 검사에서 발견된 문제가 없다는 사실만 안내한다. 초안 없음과 지적 0을 구분한다. 문장에는 번호와 안정적인 앵커가 있다 |
| DS-19 | 긴 조문과 초안을 읽을 폭을 확보한다 | 상세는 초안 → 신구조문 → 기본 정보 순서로 배치한다. 초안은 최대 48rem, 신구조문은 전체 작업 폭에서 두 칸을 사용한다. 768px 미만에서는 기존 탭을 유지한다. 모바일 가로 넘침이 없다 |
| DS-20 | 문제 설명이 내부 코드보다 먼저 읽힌다 | 지적 메시지를 먼저 표시하고 검사 단계와 규칙 ID는 접힌 상세에 둔다. 목록 ‘크리틱 적발’을 ‘확인 필요’로 바꾼다. 원문 메시지와 판정, 승인 가능 조건은 바꾸지 않는다 |

확인 대화상자는 헤더와 고정 결정 영역 위에 표시한다. 창의 배경과 뒤 배경 가림이 보여야 하며,
취소에 초기 포커스가 가고 Esc로 닫힌다. 실제 승인이나 반려 없이 이 동작을 검증한다.
