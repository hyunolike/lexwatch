# 명세: 검토 보조가 잠든 AI 서비스를 일찍 깨우고 깰 때까지 질문을 들고 기다린다 (2026-11-26)

- 작성: hh.jang
- 관련: [review-chat-ux](../review-chat-ux/spec.md), [ai-wake-retry](../ai-wake-retry/spec.md) WR-06(`ChatRetry`), [wake-wait](../wake-wait/spec.md)

## 해결할 문제

2026-11-25 23:40 UTC, 검토 화면에서 추천 질문을 보내자 82초 동안 "근거 19건을 읽고 답을 쓰는 중이에요"만 보이다가 실패했다(Render 로그).

| 시각(UTC) | 일 |
|---|---|
| 23:38:55 | API 서버가 깨어 시작 |
| 23:39:37 | 검토 화면을 열었다 |
| 23:40:13 | 검토 보조가 처음 `/api/ai/status`를 불러 AI 서비스를 깨우기 시작 |
| 23:40:17 | 질문 전송. API의 `ChatRetry`가 4초마다 AI에 보냈고 Render 프록시가 매번 바로 502를 돌려줬다 |
| 23:41:39 | 82초 뒤 `424 AI_WAKING`. 이후 요청이 없다(화면을 떠남) |
| 23:42:23 | AI 서비스 시작. 깨우기 시작 뒤 약 2분 10초 |

원인은 네 가지다. 넷째가 가장 크고, 고치는 중에 찾았다.

1. AI 서비스를 늦게 깨운다. 앱을 연 23:39:01이 아니라 검토 보조가 화면에 나온 23:40:13에 시작했다. 약 70초를 그냥 보냈다.
2. AI 상태가 "깨우는 중"인데도 질문을 바로 보낸다. 깨는 데 2분이 넘게 걸리면 서버의 90초 재시도로는 모자라고, 그 시간이 지나서야 화면이 깨기를 기다린다.
3. 그동안 안내가 "답을 쓰는 중"이라 사용자는 무엇을 기다리는지 모른다. 머리의 "AI 깨우는 중"과 말풍선 문구가 서로 다르다.
4. **API가 AI를 부르는 요청은 잠든 AI를 깨우지 못한다.** 2026-11-26 00:31 UTC에 1~3을 고친 로컬 빌드로 재현했다. 화면이 3분 동안 `/api/ai/status`를 36번 불렀고, API가 AI에 보낸 요청은 매번 0.1~0.4초 만에 502를 받았다. AI는 끝까지 깨지 않았다. 00:34:50에 AI 공개 주소로 직접 `GET /health`를 보내자 Render가 요청을 붙잡고 33.5초 뒤 200을 돌려줬다(AI 로그 00:35:23 시작). 11-25 23:42:23의 시작도 사용자의 질문이 아니라 같은 확인용 직접 요청이 깨운 것이다. Render 문서는 무료 서비스가 "들어오는 트래픽"에 깬다고만 적고, 다른 서비스가 보낸 요청은 따로 다루지 않는다. 우리 관찰로는 그런 요청은 깨우지 않는다.

넷째는 수집 잡에도 해당한다. 수집 잡의 AI 깨우기(CH-02)도 API의 `/jobs/wake-ai`를 거친다. 최근 수집 다섯 번 중 두 번(11-24 05:42, 13:45)은 3분 안에 깨지 않았고 11-25에는 수집이 실패했다([ai-wake-retry](../ai-wake-retry/spec.md)). 작업 단계 재시도(WR-02)는 기다리는 시간을 늘렸을 뿐 AI를 깨우지 않는다.

## 회고

[장애 회고 규칙](../../incident-review.md)에 따른다.

- 언제, 무엇이: 2026-11-25 23:40~23:41 UTC, 검토 보조 질문 1건이 82초 뒤 실패.
- 언제 알았나: 같은 날 23:41, 사용자가 화면 캡처와 함께 "오래 걸려 이유가 뭐야"라고 물었다. 바로 알았다.
- 같은 장애가 전에 있었나: [collect-health](../collect-health/spec.md)(11-23)와 [ai-wake-retry](../ai-wake-retry/spec.md)(11-25, 수집의 분류 단계). 두 번 모두 "AI가 깨는 데 오래 걸린다"고 보고 기다리는 시간을 늘렸다. 깨우는 요청이 실제로 AI를 깨우는지는 확인하지 않았다. 이번에 기다리는 시간과 깨우는 경로를 나눠 시험해서 찾았다.

| 갈래 | 조치 | 상태 |
|---|---|---|
| 지금 복구 | AI 서비스를 깨워 둠(`/health` 200). 다시 물으면 답한다 | 완료 |
| 감지 | 해당 없음. 사용자가 바로 보는 실패라 화면 문구로 알린다(CW-03) | — |
| 피해 줄이기 | 앱을 열 때 깨우기 시작(CW-01) | 이 명세 |
| 예방 | 브라우저와 수집 잡이 AI 공개 주소로 직접 깨운다(CW-05, CW-06). 깨기 전에는 질문을 보내지 않고 들고 기다린다(CW-03) | 이 명세 |
| 배포 뒤 확인 | AI가 잠든 상태에서 앱을 열고 질문했을 때 "깨우는 중" 문구 뒤 답이 오는지 | 배포 뒤 이슈 |

## 요구사항

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| CW-01 | 앱을 열 때 AI 서비스를 깨운다 | 레이아웃의 클라이언트 컴포넌트가 처음 그려질 때 한 번 AI 깨우기를 시작한다. 깨우기는 `/api/ai/status`를 5초 간격으로 최대 3분 부른다. 페이지 이동으로는 다시 시작하지 않는다 |
| CW-02 | 깨우기는 한 곳에서 한 번만 돈다 | `createAiWaker`가 상태(`checking`, `up`, `waking`)를 들고, 진행 중인 깨우기가 있으면 새로 시작하지 않고 그것을 돌려준다. 1분 안에 `up`을 확인했으면 다시 묻지 않는다. 검토 보조는 이 상태를 구독한다 |
| CW-03 | 깨기 전에는 질문을 보내지 않는다 | 보내기를 누르면 먼저 깨우기를 기다린다. 기다리는 동안 말풍선은 "AI 서버를 깨우는 중이에요. 길면 2~3분 걸려요. 깨어나면 이 질문을 자동으로 보낼게요."이고, 깨면 그때 보낸다. 3분 안에 깨지 않으면 보내지 않고 "서버를 깨우는 중이에요. 잠시 뒤에 다시 물어봐 주세요."를 보인다 |
| CW-05 | 브라우저가 AI를 직접 깨운다 | 깨우기가 상태를 물을 때마다 `NEXT_PUBLIC_AI_WAKE_URL`(AI의 `/health` 공개 주소, `netlify.toml`)로 `no-cors` GET을 보낸다. 앞의 요청이 끝나기 전에는 새로 보내지 않는다(Render가 깰 때까지 붙잡으므로). 주소가 없으면(로컬 개발) 보내지 않는다. 실패해도 상태 확인은 계속한다. AI의 `/health`는 토큰 없이 열려 있고 모델을 부르지 않는다 |
| CW-06 | 수집 잡이 AI를 직접 깨운다 | `collect.yml`의 AI 깨우기 단계가 매 시도마다 `AI_PUBLIC_URL/health`를 먼저 부르고(최대 60초) 그 다음 `/jobs/wake-ai`로 API에서 가는 길을 확인한다. 감시 단계의 1분 간격 깨우기에도 직접 요청(최대 30초)을 더한다 |
| CW-04 | 깨어 있다고 본 뒤 잠든 경우도 다룬다 | 보낸 질문이 `AI_WAKING`(또는 API가 깨는 중)으로 돌아오면 지금처럼 깨기를 다시 기다렸다가 한 번 더 보낸다. 이때 상태를 바로 `waking`으로 바꿔 문구도 바뀐다 |

## 범위 밖

- AI 서비스를 유료 인스턴스로 바꾸는 일. 비용 결정이라 사용자가 정한다.
- 예약 핑으로 깨워 두는 일. Render가 무료 인스턴스 남용으로 본다([ai-wake-retry](../ai-wake-retry/spec.md) 범위 밖).
- API 서버(.NET)가 AI 공개 주소로 깨우기 요청을 보내는 일. 바깥 요청만 깨운다는 관찰과 맞지 않을 수 있어, 확인된 두 경로(브라우저, GitHub Actions)만 쓴다. 작업 단계 재시도 중에 AI가 잠드는 경우는 감시 단계의 1분 간격 직접 요청이 막는다.
- 서버 `ChatRetry`의 90초 마감 변경. 화면이 깨기를 먼저 기다리므로 그대로 둔다.
