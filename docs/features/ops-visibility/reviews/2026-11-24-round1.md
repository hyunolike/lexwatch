# EGM 검토 1차 (2026-11-24)

- 대상: [spec.md](../spec.md), [design.md](../design.md) 초안
- 검토자: Goldfish 두 명. 설계 비평(egm-design)과 구현 준비도(egm-implementation-readiness)다. 새 문맥으로 실행했고 부모 대화는 넘기지 않았다.
- 두 검토가 같은 지적을 낸 경우가 많아 하나로 묶었다.

## 지적과 조치

| # | 심각도 | 지적(출처) | 조치 |
|---|---|---|---|
| 1 | 높음 | 진행 중 행의 소요 시간은 앞 시도의 값이 남아 있어(StepQueue가 지우지 않음) 끝난 막대처럼 그려진다. 재시도 대기 행을 그리는 규칙이 없다(설계, 준비도) | 반영. 진행 중은 `now - start`로 그리고, 재시도 대기는 마지막 시도 막대에 실패 톤과 "재시도 대기"를 단다. 예정 시각은 응답에 없어 그리지 않는다. 테스트 두 건 추가 |
| 2 | 높음 | 60초 이하 빈 구간이 선형이라 그래프가 수천 px가 될 수 있다(설계) | 확인. 바쁜 구간에 60초 이하 빈 시간을 포함해 축척을 정하므로 폭은 `720 + 28 × 접힌 수`다. 설계 문구가 이를 분명히 하지 않아 고쳤고, 폭 불변식을 테스트한다 |
| 3 | 높음 | 재현 02의 재시도는 행을 나눠 담아 "관리자 다시 실행"처럼 보이고, 실제 자동 재시도는 "시도 N"으로만 보여 같은 개념이 두 모양이다(설계) | 반영. 두 번째 이후 기록은 원인을 단정하지 않는 "다시 시도한 기록"으로 표시하고, 데이터 차이를 알려진 한계에 적었다. 픽스처는 바꾸지 않았다(재현 녹화의 의미를 바꾸는 일이라 범위 밖) |
| 4 | 높음 | "AI 호출 수"가 실제 호출이 아니라 최종 공급자를 세고, 실패 행(none)과 fallback이 섞여 합계가 맞지 않는다(설계, 준비도) | 반영. 이름을 "AI 처리(최종 공급자 기준)"로 바꾸고 모델 공급자만 센다. 규칙 대체와 실패는 따로 낸다. 일별 합 = 합계 등식을 테스트한다 |
| 5 | 높음 | 재현 제외 규칙을 채팅과 결정에 어떻게 적용하는지 없다(준비도) | 반영. 채팅은 외래키가 없어 모두 세고, 결정은 비재현 그룹만 센다. 공개 데모에서 결정 지표가 0에 가까울 수 있다고 한계에 적었다 |
| 6 | 중간 | 기록 단위 실패율은 다시 실행으로 성공해도 실패로 남고, "다시 실행 수"는 상류 재실행으로 부풀려진다(설계) | 반영. 실패율은 (실행, 단계, 그룹)의 마지막 기록 기준이다. 다시 실행 수는 원인을 가릴 수 없어 "다시 시도한 기록"으로 이름을 낮췄다 |
| 7 | 중간 | 작은 표본에서 p90과 비율, 스파크라인이 과장된다(설계) | 반영. 비율과 소요 시간 옆에 분모와 n을 적고, 표본 5개 미만이면 p90을 null로 낸다. 스파크라인은 실행 수와 AI 처리 두 카드에만 단다 |
| 8 | 중간 | 결정까지 걸린 시간은 노이즈인데 숫자 카드에 있고, 시작점(분석 종료)이 결정 가능 시점과 다르며, 기준 기록이 모호하다(설계, 준비도) | 반영. 카드에서 빼서 결정 영역 보조 글(n 포함)로 내렸다. 시작점은 결정 전 마지막 3단 판정 종료(없으면 분석, 근거 부족 포함)다. 중앙값은 짝수면 평균이다 |
| 9 | 중간 | 병목 비율의 분모가 문서마다 다르고, 분석 단계는 거의 늘 절반을 넘어 경고가 늘 켜진다(설계, 준비도) | 반영. 분모는 끝난 막대 구간의 합집합 길이이고, 경고 톤은 쓰지 않는다 |
| 10 | 중간 | 막대 상세가 툴팁에만 있어 터치에서 볼 수 없고, 버튼 수십 개와 sr-only 표가 중복이다(설계) | 반영. 막대는 대화형이 아니고, 소요 시간, 상태, 오류 코드, 시도를 막대 옆 글로 늘 보인다. 그래프는 스크린리더에서 숨기고 "목록" 탭이 글 대안이다 |
| 11 | 중간 | 적발 비율이 검사가 끝나기 전의 초안을 "적발 없음"으로 센다(설계, 준비도) | 반영. 3단 판정이 끝난 그룹의 초안만 센다 |
| 12 | 중간 | 응답 형태: 실행 상태 키 누락, 수집 기록의 듬성한 배열, notify 누락, null과 반올림, 날짜 귀속(준비도) | 반영. 상태 여섯 키, 날짜에 맞춘 수집 배열(null과 0 구분), 단계 여덟 개, null 가능 필드와 반올림, 날짜 귀속 표를 설계에 적었다 |
| 13 | 낮음 | days가 숫자가 아니면 프레임워크 400이 먼저 난다. 관리자가 아니어도 API를 부른다(준비도) | 반영. 문자열로 받아 직접 해석하고, 관리자가 아니면 부르지 않는다 |
| 14 | 낮음 | 담당 매핑 위치, notify 담당, 결정 라벨, 링크된 문서 부재(준비도) | 반영. 매핑은 `lib/runTimeline.ts`의 `stepActor`(notify는 규칙)이고, 결정 라벨은 역할과 결정과 그룹이다. 작업과 검토 문서를 만들었다 |

## 남은 쟁점

없다. 재검토는 구현 뒤 코드 리뷰로 대신한다.
