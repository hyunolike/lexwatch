## 해결할 문제

LexWatch는 단계별 재시도, 대체 경로(NVIDIA → Cloudflare → 규칙), 수집 감시, AI 사용 기록을 구현했다. 하지만 화면에서는 이것이 숫자와 목록으로만 보인다.

- **실행 상세:** 단계가 세로 카드 목록이다. 어느 단계가 시간을 많이 썼는지, 실패 뒤 언제 다시 실행됐는지를 숫자를 하나씩 읽어야 안다.
- **실행 현황:** 며칠 동안 몇 건을 처리했고 얼마나 실패했는지, AI 호출이 어느 공급자로 갔는지를 한 화면에서 볼 수 없다. AI 사용 기록은 검토 보조 채팅만 센다.

외부 근거는 다음과 같다(출처는 설계 끝).

- **Temporal Web UI:** 워크플로 실행을 시간축 타임라인으로 보인다. 재시도에는 시도 번호를 단다.
- **Langfuse, LangSmith:** 에이전트 단계를 워터폴로 보이고, 전체 시간의 큰 몫을 쓴 단계를 색으로 강조한다.
- **Stephen Few:** 대시보드는 한 화면에서 한눈에 보는 것이다. 숫자 옆에 작은 추세선(스파크라인)을 두고, 게이지 대신 위치와 길이로 표현한다.

## 범위

- 포함: 실행 상세의 타임라인 보기, 관리자용 운영 현황 화면과 집계 API.
- 제외: 시행일 캘린더, 실행 이력 목록 정리, 법안 레이더 단계 분포. 다음 작업으로 둔다. 경보(알림 발송)도 제외한다.

## 요구사항

### 실행 타임라인

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| OV-01 | 보기를 고른다 | 실행 상세에 "목록"과 "타임라인" 탭이 있다. 기본은 지금의 목록이다. 탭은 키보드(좌우 화살표)로 옮긴다 |
| OV-02 | 단계를 막대로 그린다 | 단계 기록마다 시작 시각부터 소요 시간만큼 가로 막대를 그린다. 줄은 (단계, 그룹)마다 하나이고, 처음 시작한 순서로 놓는다(같으면 단계 순서, 그룹 코드 순). 상태별로 다음과 같다.<br>- 대기: 예정 시각에 빈 표시<br>- 진행 중: 남아 있는 소요 시간 값은 앞 시도의 것이라 무시하고, 지금까지 지난 시간으로 그린다<br>- 재시도 대기: 마지막 시도 막대를 실패 톤으로 그리고 "재시도 대기"를 단다. 다음 예정 시각은 응답에 없어 그리지 않는다<br>같은 줄의 두 번째 이후 기록(관리자 다시 실행, 재현 데이터의 재시도 기록)에는 "다시 시도한 기록"을 단다. 도구 호출, 적발, 알림 항목은 그리지 않는다 |
| OV-03 | 담당과 상태를 구분한다 | 막대 색은 AI 사용 드러내기의 담당 구분(AI, 규칙)을 따른다. 대체 구현(fallback)은 규칙이고, 알림(notify)도 규칙이다. 실패는 빗금과 "실패 오류코드" 글, 확인 필요는 경고 테두리와 글로 보인다. 시도가 2회 이상이면 "시도 N"을 단다. 색만으로 구분하지 않는다 |
| OV-04 | 병목을 보인다 | 끝난 기록(성공, 실패, 확인 필요) 중 소요 시간이 가장 긴 것을 "가장 오래 걸림"으로 표시하고, 위에 "가장 오래 걸린 단계: 분석 금융, 23.8초 (단계가 실제로 돈 시간의 68%)"를 적는다. 분모는 끝난 막대 구간의 합집합 길이다. 분석 단계는 구조적으로 거의 늘 절반을 넘으므로 경고 톤은 쓰지 않는다 |
| OV-05 | 빈 시간을 접는다 | 막대와 결정 점 사이에 60초 넘게 아무 일도 없던 구간은 고정 폭(28px)으로 접고 축 위에 "⋯ 32분"을 적는다. 60초 이하의 빈 시간은 바쁜 구간에 넣어 선형으로 그린다. 축척은 접히지 않은 구간 전체를 목표 폭(720px)에 맞추므로 그래프 폭은 720px + 접힌 구간 수 × 28px다 |
| OV-06 | 사람 결정 | 승인, 반려, 파트너 결정은 결정 시각에 점과 글("변호사 승인")로 보인다. 결정까지 걸린 시간은 접힌 구간에 들어간다 |
| OV-07 | 읽을 수 있다 | 축 왼쪽에 시작 시각(KST)을 적는다. 줄 왼쪽에 담당 배지, 단계 이름, 그룹을 두고, 막대 오른쪽에 소요 시간, 상태, 오류 코드, 시도를 글로 늘 보인다(툴팁에만 두면 터치에서 볼 수 없다). 그래프는 스크린리더에서 숨기고, "목록" 탭이 같은 내용의 글 대안이라고 알린다. 범례를 글로 둔다. 375px에서 페이지는 가로로 넘치지 않고 그래프 영역만 가로 스크롤된다 |

### 운영 현황

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| OV-10 | 집계 API | `GET /api/ops/summary?days=14`는 관리자만 볼 수 있다(그 밖 403). days는 7, 14, 30 중 하나이고 없으면 14, 숫자가 아니거나 그 밖이면 400 `INVALID_DAYS`다. 기간은 KST 기준 (오늘 - days + 1)일 00:00부터 지금까지다. 일별 배열은 그 날짜들에 맞춘 days개다. 재현 실행의 단계, 그룹, 초안, 결정은 뺀다. 채팅 기록은 외래키가 없어 재현 여부를 가릴 수 없으므로 모두 센다 |
| OV-11 | 처리량 | 기간 안에 만든 실행 수와 일별 수, 실행 상태 여섯 가지(대기, 진행 중, 검토 중, 완료, 관련 없음, 실패)별 수. 아침 수집 기록은 날짜에 맞춘 배열로 내고, 기록이 없는 날은 null, 0건인 날은 0이다 |
| OV-12 | 단계 신뢰성 | 단계 여덟 개(수집부터 알림까지)마다 낸다. 실패율은 **최종 결과 기준**이다. 같은 (실행, 단계, 그룹)의 마지막 기록이 실패인 것만 실패로 센다. 다시 실행해 성공했으면 실패가 아니다. 함께 내는 값은 자동 재시도 횟수(Σ max(시도-1, 0)), 다시 시도한 기록 수(같은 실행과 그룹의 두 번째 이후 기록. 관리자 다시 실행과 상류 재실행으로 생긴 기록을 구분하지 못해 이 이름을 쓴다), 성공 기록 소요 시간의 표본 수, 중앙값, 90번째 백분위(표본 5개 미만이면 null)다. 기간은 기록의 종료 시각(없으면 시작 시각) 기준이다. 전체 최종 실패율과 분모도 낸다 |
| OV-13 | AI 공급자 | AI 단계(분류, 색인, 분석, 판정)의 끝난 기록을 **최종 공급자** 기준으로 센다. 실제 호출 수가 아니다(대체 경로의 앞선 시도와 에이전트 안의 여러 호출은 세지 않는다). 모델 공급자(nvidia, cloudflare, groq)만 "AI 처리"이고, 규칙 대체(fallback)와 실패는 따로 낸다. 채팅은 결과별, 공급자별로 낸다. "AI 처리" 합계와 일별 배열은 (모델 공급자인 단계 기록 + 모델이 답한 채팅)이며 서로 합이 같다 |
| OV-14 | 검수 | 기간 안에 분석이 성공하고 3단 판정까지 끝난 그룹의 최신 에이전트 초안 수(그룹마다 하나), 그중 적발이 1건 이상인 초안 수와 비율, 단(1, 2, 3)별 적발 건수. 검사가 끝나기 전의 초안은 "적발 없음"으로 세지 않는다 |
| OV-15 | 사람 결정 | 기간 안의 결정 수(종류별)와 지금 결정을 기다리는 비재현 그룹 수(검토 필요, 승인 대기, 파트너 승인 대기). 결정까지 걸린 시간은 그룹의 첫 변호사 승인이나 반려가 기간 안일 때, 그 결정 전에 끝난 마지막 3단 판정(없으면 분석, 근거 부족 포함)의 종료 시각부터 잰다. 중앙값(짝수면 가운데 두 값의 평균)과 표본 수를 낸다. 숫자 카드에는 올리지 않고 결정 영역의 보조 글로 둔다(방문자 클릭이 섞인다) |
| OV-16 | 법안 수집 | 법안 레이더 수집 기록의 마지막 성공 시각과 기간 안의 실패 실행 수 |
| OV-17 | 화면 | 관리자 머리 메뉴에 "운영 현황"이 생긴다. 관리자가 아니면 API를 부르지 않고 안내만 보인다. 맨 위에 기간 선택(7, 14, 30일)과 숫자 카드 네 개가 있다.<br>- 실행 수(스파크라인)<br>- 단계 최종 실패율<br>- AI 처리(최종 공급자 기준, 스파크라인)<br>- 적발 있는 초안 비율<br>카드마다 분모를 글로 적는다. 아래 세 영역이 있다.<br>- 단계별 실패율과 소요 시간: 같은 축의 가로 막대 목록, 표본 수 표시<br>- AI 공급자: 100% 누적 막대와 범례 글, 규칙 대체, 실패, 채팅 결과<br>- 사람 결정: 대기 수, 종류별 수, 결정까지 걸린 시간(n), 법안 수집 상태<br>차트 값은 모두 글로도 보인다. 375px에서 가로로 넘치지 않는다 |

## 알려진 한계

- 단계 기록은 한 행에 마지막 시도의 시작 시각과 소요 시간만 남는다. 같은 행 안의 앞선 자동 재시도는 막대로 그리지 못하고 "시도 N"으로만 보인다. 재시도 대기 시간도 따로 보이지 않는다.
- 재현 데이터는 시도마다 행을 나눠 담는다(시도 0, 1). 실제 자동 재시도는 같은 행의 시도 번호를 올린다. 그래서 재현 실행의 재시도는 "다시 시도한 기록"으로 보인다.
- "AI 처리"는 실제 호출 수가 아니다. 호출 단위 로그가 필요하면 별도 작업이다.
- 결정까지 걸린 시간에는 공개 데모의 특성상 방문자의 클릭이 섞인다. 공개 데모의 결정 대부분은 재현 예시에서 일어나 집계에서 빠지므로 0에 가까울 수 있다.
- 비재현 실행은 하루 몇 건이라 단계별 표본이 작다. 모든 비율과 소요 시간 옆에 표본 수를 적는다.
