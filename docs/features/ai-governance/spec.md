# 명세: AI 거버넌스 (2026-11-24)

- 작성: hh.jang
- 관련: [설계](design.md), [작업](tasks.md), [승인 전 적발 확인](../approval-guard/spec.md), [전체 설계 문서](../../superpowers/specs/2026-11-16-lexwatch-design.md)

## 해결할 문제

대형 로펌은 생성형 AI를 들이면서 두 가지 통제를 함께 둔다. 하나는 고객 정보와 개인정보가 AI로 넘어가지 않게 입력을 관리하는 것이고, 다른 하나는 AI가 만든 결과물을 변호사가 교차검토하는 것이다. 법무법인 태평양도 2026-07-01 Harvey 전사 도입을 알리면서 "민감정보 입력 관리"와 "결과물에 대한 변호사의 교차검토 절차"를 AI 거버넌스로 운영한다고 밝혔다([법인소식](https://www.bkl.co.kr/law/insight/information/6555)).

LexWatch에는 두 통제가 없다.

1. **검토 보조 채팅은 변호사가 친 글을 그대로 AI 서비스와 외부 모델(NVIDIA 등)로 보낸다.** 변호사가 "○○전자(주민번호 900101-1234567 대표) 사건에 적용되나요?"라고 물으면 고객명과 주민등록번호가 그대로 외부 모델로 나간다. 입력 레일(guardrails)은 프롬프트 주입과 법률 자문 요청만 거절하고 민감정보는 보지 않는다. 그 검사도 AI 서비스 안에서 하므로, 원문은 이미 API 경계를 넘은 뒤다.
2. **AI를 언제, 무엇에 썼는지 남는 기록이 없다.** 채팅은 개인정보 보호를 위해 저장하지 않으므로, 관리자는 민감정보가 몇 번 걸렸는지, 채팅이 얼마나 거절됐는지 알 수 없다.
3. **적발이 남은 초안도 변호사 한 명이 승인하면 바로 나간다.** 승인 직전 재검사(approval-guard)는 변호사가 적발 수를 확인하게 할 뿐, 두 번째 사람이 보지 않는다.

## 범위

- 포함: 검토 보조 채팅 입력의 민감정보 가리기(API에서), AI 사용 기록과 관리자 화면, 적발이 남은 승인의 파트너 최종 승인
- 제외: Workflow 단계(분류, 분석, 크리틱)의 모델 입력 가리기. 입력이 공포된 법령 원문(공개 자료)뿐이라 가릴 대상이 없다. 단계별 모델 사용은 이미 실행 이력(step_runs)에 공급자와 함께 남는다.
- 제외: 실제 로그인과 사람 단위 신원. 데모는 역할 헤더로 사람을 구분한다. 그래서 "다른 사람"은 "다른 역할"로 대신한다(알려진 한계).
- 제외: 이름 같은 자유 형식 개인정보의 자동 인식(NER). 규칙으로 잡을 수 있는 형식과 법인이 등록한 고객사 이름만 다룬다.

## 요구사항

### 민감정보 입력 관리

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| GV-01 | 형식이 있는 민감정보를 찾는다 | 주민등록번호와 외국인등록번호(`######-#######`, 공백 구분과 붙여 쓴 13자리 포함. 앞 6자리의 월이 01~12, 일이 01~31이고 7번째 자리가 1~8일 때만), 휴대전화와 일반전화(`010-1234-5678`, `010 1234 5678`, `02-123-4567`, 붙여 쓴 `01012345678`), 이메일, 카드번호(붙여 쓴 13~19자리, 같은 구분자로 4-4-4-(1~7), Amex 4-6-5. Luhn 검사 통과), 사업자등록번호(`###-##-#####`), 계좌번호(하이픈으로 나뉜 3~4덩이, 숫자 합 10~14자리, 날짜로 시작하면 제외), 여권번호(영문 1자 + 숫자 8자리)를 찾는다. 법령 문장에 흔한 조문번호(`제2조의3`), 날짜(`2026-11-24`, `2026. 11. 24.`, 이어 쓴 `2026-11-24 2026-12-31`, `2026-11-24-01`), 금액(`3,000,000원`), 비율(`100분의 50`)은 잡지 않는다 |
| GV-02 | 등록한 고객사 이름을 찾는다 | 설정 `Governance:ClientNames`(쉼표 구분)에 있는 이름이 문장에 있으면 찾는다. 대소문자와 앞뒤 공백은 무시하고 부분 문자열도 가린다(`한빛전자공업` → `[고객사]공업`). 고객사 이름을 형식 규칙보다 먼저 가린다. 공개 데모에는 가상의 고객사 이름(`한빛전자`, `가람바이오`, `누리캐피탈`)을 둔다 |
| GV-03 | 찾은 값을 가리고 보낸다 | 검토 보조 채팅의 질문과 대화 기록의 사용자 턴을 AI 서비스로 보내기 전에 API가 가린다. 찾은 값은 `[주민등록번호]`, `[전화번호]`, `[이메일]`, `[카드번호]`, `[사업자등록번호]`, `[계좌번호]`, `[여권번호]`, `[고객사]`로 바꾼다. 순서는 원문 길이 검사(1~500자), 원문 전체 가리기, AI 계약 한도(질문 500자, 기록 턴 2000자)로 자르기다. 자를 때 자리표시 중간에서 끊지 않는다. 원문은 API 밖으로 나가지 않고 로그와 DB에도 남지 않는다. 가린 뒤 질문이 자리표시만 남아도 그대로 보낸다(입력 레일이 거절한다) |
| GV-04 | 가린 사실을 알린다 | 채팅 성공 응답에 `maskedQuestion`(가린 질문)과 `masked: [{ kind, label, count }]`(이번 질문에서 찾은 것만, 없으면 빈 배열)가 있다. 대화 기록도 가리지만 건수에는 넣지 않는다(이전 질문에서 이미 센 것이다). 화면은 사용자 말풍선을 가린 질문(`maskedQuestion`)으로 바꾸고 그 아래에 "민감정보를 가리고 보냈어요: 주민등록번호 1건"을 보인다. 여러 종류면 응답 순서대로 "주민등록번호 1건, 고객사 2건"처럼 쉼표로 잇는다. 다음 질문의 대화 기록에는 가린 문장이 들어간다. 오류 응답(429, 424, 깨우는 중)에서는 말풍선을 바꾸지 않는다. 다음 요청 때 서버가 기록을 다시 가린다 |

### AI 사용 기록

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| GV-05 | 채팅 요청마다 기록을 남긴다 | 할당량을 통과한 검토 보조 요청마다 `ai_usage_logs`에 한 행: 시각, 용도(`review_chat`), 검토 ID, 역할, 결과(`answered`, `refused`, `unavailable`=모델 키가 없는 환경의 고정 응답, `failed`=AI 실패, 예외, 요청 취소), 공급자 종류와 이름(failed면 없음), 소요 시간(AI 호출 직전부터 응답까지 ms), 이번 질문에서 가린 종류별 건수. 질문, 답변, IP는 남기지 않는다. 90일이 지난 기록은 매일 데모 초기화 작업이 지운다. 기록 저장이 실패해도 채팅 응답은 그대로 돌려준다 |
| GV-06 | 관리자가 기록을 본다 | `GET /api/governance/ai-usage`는 관리자만(그 밖 403). 최근 100건(최신순)과 최근 7일(지금부터 168시간) 요약을 돌려준다. 요약은 요청 수, 결과별 수(네 결과 모두 0이어도 키를 낸다), 가린 종류별 합계, 공급자 종류별 수(공급자가 없는 failed는 빼고)다. lawyer와 partner는 403이다. 웹 `/governance` 화면이 이를 표와 숫자로 보이고, 관리자 역할일 때만 머리 메뉴에 "AI 사용 기록"이 보인다 |

### 교차검토(파트너 최종 승인)

| ID | 요구사항 | 수용 기준 |
|---|---|---|
| GV-07 | 적발을 확인하고 승인하면 파트너를 기다린다 | 변호사 승인에서 승인 직전 재검사의 적발이 1건 이상이면(approval-guard AG-04를 통과한 경우) 상태가 `AwaitingPartner`가 되고 알림은 큐에 넣지 않는다. 승인 기록(`decision=approve`, `actorRole=lawyer`, 확인한 적발 수)과 수정본은 지금처럼 남고, 승인 기록에 그때 확인한 적발 목록(`findingsJson`)을 고정해 둔다. 파트너가 한 번이라도 돌려보낸 그룹은 다음 변호사 승인이 적발 0건이어도 `AwaitingPartner`로 간다. 적발 0건 승인은 지금과 같이 바로 `Approved`가 되고 알림이 나간다 |
| GV-08 | 파트너가 최종 승인한다 | `POST /api/reviews/{id}/confirm`(`{ version, comment? }`)은 `X-Demo-Role: partner`만. `AwaitingPartner`이고 버전이 맞으면 `Approved`가 되고 알림이 큐에 들어간다. 승인 기록 `decision=confirm`, `actorRole=partner`가 남는다. 상태가 다르거나 버전이 다르면 409 `REVIEW_ALREADY_DECIDED` |
| GV-09 | 파트너가 돌려보낸다 | `POST /api/reviews/{id}/return`(`{ version, comment }`, 사유 필수, 없으면 400 `COMMENT_REQUIRED`)은 파트너만. `AwaitingPartner`를 `NeedsReview`로 되돌리고 기록 `decision=return`, `actorRole=partner`가 남는다. 변호사는 다시 승인, 수정 후 승인, 반려할 수 있다 |
| GV-10 | 역할을 나눈다 | 파트너는 `WaitingApproval`과 `NeedsReview`를 승인하거나 반려할 수 없고(403), 변호사는 confirm과 return을 할 수 없다(403). 관리자는 둘 다 못 한다. 검토 보조 채팅은 변호사만 쓴다(지금과 같다) |
| GV-11 | 화면이 단계를 보인다 | 역할 전환에 "파트너로 보기"가 생긴다. 승인 대기함 기본 목록에 `AwaitingPartner`가 들어가고 라벨은 "파트너 승인 대기"다. 검토 화면은 `AwaitingPartner`일 때 변호사의 승인 시각과 그때 확인한 적발 목록을 보여 주고, 파트너에게만 "최종 승인"(확인 대화상자)과 "돌려보내기"(사유 입력) 버튼을 준다. 변호사가 적발을 확인하고 승인하면 "파트너 최종 승인을 기다려요"를 알린다. 실행 이력 타임라인에 confirm과 return 기록이 라벨("파트너 최종 승인", "파트너가 돌려보냄")과 함께 보인다 |
| GV-12 | 실행 상태가 맞게 바뀐다 | `AwaitingPartner`는 끝나지 않은 그룹이다. 남은 단계가 없고 열린 그룹이 모두 사람 결정(`WaitingApproval`, `NeedsReview`, `AwaitingPartner`)을 기다리면 실행은 `InReview`다. 관리자의 실패 단계 다시 실행은 `AwaitingPartner` 그룹의 단계를 다시 큐에 넣지 않는다 |
| GV-13 | 분석이 끝난 뒤에만 결정한다 | 그 그룹의 단계가 아직 대기, 실행, 재시도 예정이면 승인, 반려, confirm, return이 모두 409 `ANALYSIS_IN_PROGRESS`다. 단계가 끝나면서 그룹 상태를 덮어써 결정이 사라지는 일을 막는다 |
| GV-14 | 알림에 교차검토가 드러난다 | 파트너 최종 승인을 거친 알림의 본문 끝은 "(승인: 변호사 YYYY-MM-DD HH:mm, 파트너 최종 승인 YYYY-MM-DD HH:mm)"이다. 거치지 않은 알림은 지금과 같다 |

## 알려진 한계

- 데모는 로그인이 없어 "다른 사람"을 역할로만 구분한다. 지금은 역할 검사만 하며, 같은 사람 검사는 없다. 한 사람이 역할을 바꿔 두 번 승인할 수 있다. 실제 배포에서는 SSO 신원을 승인 기록에 남기고 confirm에서 변호사 승인자와 다른 사람인지 확인해야 한다.
- 입력 레일이 거절한 사유(주입, 법률 자문, 범위 밖)는 AI 응답에 없어 기록하지 않는다.
- 규칙 기반 탐지라 형식이 없는 정보(사람 이름, 주소, 사건 내용)는 잡지 못한다. 화면 안내 문구에 이 한계를 적는다.
- 공백으로 나뉜 계좌번호와 주민등록번호 이외의 공백 구분 숫자는 잡지 않는다.
- 계좌번호는 은행마다 형식이 달라 하이픈 없는 숫자열은 잡지 않는다(전화번호, 카드번호와 섞여 오탐이 많다).

## 오류 상황

- 가리기는 결정적 규칙이라 실패하지 않는다. 설정의 고객사 이름이 비어 있으면 형식 탐지만 한다.
- 기록 저장이 실패하면 경고 로그(가린 종류와 수만)를 남기고 채팅 응답은 그대로 간다. 채팅 할당량 반환 규칙은 지금과 같다.
- 파트너 최종 승인과 변호사의 다른 동작이 겹치면 낙관적 동시성(xmin)으로 한쪽이 409를 받는다.
