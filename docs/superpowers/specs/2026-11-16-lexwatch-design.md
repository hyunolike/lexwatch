## 1. 왜 만드는가

공고의 주요 업무는 "AI Agent, LLM, 외부 API를 활용한 업무 자동화 Workflow 설계·개발"이고, 우대사항은 RAG·Vector DB, 예외 처리·실행 이력·모니터링, React/Next.js, Docker, 법률 분야 경험이다. 지원자는 필수 요건(경력 4년 10개월, C#/.NET, REST, SQL)을 충족하지만 이력서에 AI Agent와 Python 실적이 한 줄씩 흩어져 있다. 이 데모는 그 빈칸을 **실제로 돌아가는 서비스**로 메운다.

평가자(법인 IT팀 실무자)가 링크를 열었을 때 읽혀야 하는 것은 넷이다.

1. 법인에 실제로 있는 업무를 자동화했다. 대형 로펌은 법령 개정을 감시해 실무그룹별로 고객 안내(Legal Update)를 낸다.
2. 외부 데이터를 받아 여러 단계로 흘러가는 Workflow를 설계했고, 그 안에서 AI Agent가 도구를 골라 쓴다.
3. 실패와 LLM 오답을 사람이 통제할 수 있다. 실행 하나를 열면 단계, 재시도, 에이전트의 도구 호출, 크리틱 판정, 승인자가 한 화면에 이어진다.
4. 법인 데이터가 밖으로 나가지 않는 구조로 옮길 수 있다. 모델은 NVIDIA NIM으로 호출하므로 같은 API로 법인 내부 GPU에 올릴 수 있다.

## 2. 목표 · 하지 않을 것 · 실패로 칠 것

**목표**
- 국가법령정보센터 Open API로 **공포된 법령 개정**을 매일 수집한다.
- 실무그룹(노동, 개인정보, 금융 세 그룹으로 시작)별로 관련 있는 개정만 골라낸다.
- 영향 분석 에이전트(Nemotron)가 근거를 인용한 메모 초안을 쓴다.
- 크리틱 3단이 초안을 검사한다.
- 변호사 역할 사용자가 승인해야 알림이 나간다.
- 모든 실행의 단계별 이력, 재시도, 에이전트 도구 호출, 크리틱 판정, 승인 기록을 남기고 화면에서 따라갈 수 있다.
- 배포된 주소가 채용 결과 발표(2027년 1월 초)까지 동작한다.

**하지 않을 것**
- 입법예고 수집(9절 결정 1). 첨부 HWP·PDF 파싱이 필요하고 출처 API가 다르다. 향후 계획으로만 적는다.
- 판례 전문 검색 서비스, 범용 법률 챗봇.
- 실제 사건, 의뢰인, 법인 내부 문서를 흉내 낸 데이터. 공개 법령 데이터만 쓴다.
- 회원 가입, 다중 조직, 권한 체계 전반. 데모 역할 두 개(변호사, 관리자)면 된다.
- 노코드 Workflow 도구, 외부 Workflow 엔진(Temporal, Hangfire), 메시지 큐, Kubernetes.
- 쓸 이유가 없는 NVIDIA 기술(cuOpt, BioNeMo, NemoClaw 전체 구성).

**실패로 칠 것 (동작해도)**
- 근거 조문 없이 문장을 만들어 내는 초안. 근거 없는 문장은 표시되거나 걸러져야 한다.
- 에이전트가 "적용된다/안 된다"를 단정하는 화면. 불확실성이 보여야 한다.
- 링크를 열었는데 빈 화면이거나 오류인 상태.
- 재현한 실행을 실제 운영 이력처럼 보이게 하는 것.
- 대체 구현이 돌았는데 NVIDIA가 돈 것처럼 표시하는 것.
- "변호사 대체" 같은 표현.

## 3. 제약

- 기간 9일, 1인 개발. 범위는 줄이되 화면에 보이는 것은 전부 끝까지 동작해야 한다.
- 비용은 무료 구간 안. NVIDIA 호스팅 API(build.nvidia.com) 무료 크레딧을 쓴다.
- 국가법령정보센터 Open API는 사용자 ID(OC) 신청이 필요하고, 오퍼레이션별 활용 신청이 따로 필요할 수 있다. 첫날 신청하고 실호출로 확정한다.
- 이 계열 공공 API는 잘못된 파라미터에 오류 대신 빈 결과를 줄 수 있다. 응답을 녹화해 테스트 픽스처로 쓴다.
- NVIDIA 무료 엔드포인트는 429·5xx를 자주 돌려준다(ReRoute 실측: 실행마다 13~21회). 재시도와 대체 경로가 필수다.
- Nemotron의 한국어 법률 문장 품질은 미검증이다. 첫날 시험한다(11절).

## 4. 검토한 방법

| 방법 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. .NET 단일 백엔드 + Next.js | 실무 언어 하나로 깊이, 배포 단순 | Python 근거 없음, NVIDIA 어댑터 재사용 불가 | 기각 |
| **B. .NET(Workflow) + Python FastAPI(AI) + Next.js** | 공고의 Python/C# 둘 다 보여 줌, ReRoute의 NVIDIA 어댑터 재사용, AI 쪽 교체가 핵심에 번지지 않음 | 서비스 하나 더 배포, 계약·추적 연결 필요(약 1일) | **선택 (지원자 결정)** |
| C. n8n 등 노코드 + LLM 노드 | 가장 빠름 | "설계·개발"이 아니라 "연결"로 보임 | 기각 |
| D. 전체를 에이전트에 맡김 | 데모가 화려해 보임 | 무엇을 할지 예측 불가, 법인이 들일 수 없는 구조 | 기각 |

에이전트는 **"바깥은 정해진 Workflow, 안쪽 한 단계만 에이전트"**로 넣는다.

LLM은 Nemotron(NIM)이 기본이다. 근거는 막는 실패다: 법인 데이터 외부 유출. NIM은 호스팅과 사내 배포가 같은 API라 주소만 바꾸면 내부 GPU로 옮겨진다. 데모는 호스팅 API로 돌리고 사내 배포 경로는 문서로 보여 준다.

## 5. 구성

```
[GitHub Actions 예약] --매일 07:00--> [.NET API: /jobs/collect]  (Render)
                                  |
                    +-------------+--------------+
                    |   Workflow 엔진 (.NET)     |
                    |   상태·재시도·이력·승인     |
                    |   크리틱 1단·2단            |
                    +---+-----------------+------+
                        |                 |
           국가법령정보센터 API      [Python AI 서비스 (FastAPI)]
              (수집, 조문 조회)        분류 · 영향 분석 에이전트 · 크리틱 3단 · 검토 보조
                        |                 |            |
                        |                 |     [NVIDIA API catalog]
                        |                 |     Nemotron(NIM) · NeMo Retriever
                    [PostgreSQL + pgvector]
                                  |
                        [Next.js 화면 (Vercel)]
```

### 5.1 .NET (ASP.NET Core, .NET 10)

맡는 일: Workflow 엔진, 수집, DB, 재시도·타임아웃 결정, 크리틱 1·2단, 승인, 알림, 화면용 API.

- EF Core + Npgsql. 마이그레이션으로 스키마를 관리한다.
- Workflow 엔진은 직접 만든다. `workflow_run`, `group_review`, `step_run` 테이블, `BackgroundService`가 `FOR UPDATE SKIP LOCKED`로 대기 단계를 집는다. 여러 인스턴스에서도 한 단계가 두 번 돌지 않는다.
- 재시도와 타임아웃은 Microsoft.Extensions.Resilience(Polly).
- Python 클라이언트는 FastAPI의 OpenAPI 문서로 생성한다(NSwag). 계약이 어긋나면 빌드에서 걸린다.
- 로그는 Serilog, 추적은 OpenTelemetry. `run_id`와 trace id를 Python으로 넘긴다.

### 5.2 Python AI 서비스 (FastAPI)

맡는 일: 판단만 한다. 실행 상태를 들지 않고 재시도 정책도 갖지 않는다(단, LLM 공급자 호출 한 번 안의 429 재시도는 어댑터가 흡수한다 — ReRoute 방식).

- `POST /classify` — 개정 한 건과 실무그룹들의 관련성, 신뢰도, 이유. NeMo Retriever로 그룹 관심사와 유사도를 먼저 구하고 Nemotron이 판정한다.
- `POST /analyze` — 영향 분석 에이전트. 7절.
- `POST /critique` — 크리틱 3단(과잉해석 판정). 8절.
- `POST /review-chat` — 검토 보조 에이전트. NeMo Guardrails로 근거 밖 질문을 거절한다.
- 입출력은 Pydantic. 실패는 구조화된 오류: `429`(재시도 시각 포함), `422`(LLM 출력 검증 실패), `200` + `insufficient_evidence`. 무엇을 할지는 .NET이 정한다.
- 공급자 추상화: `LLM_PROVIDER = nvidia | mock`, `RETRIEVER_PROVIDER = nvidia | lexical`. 키가 없거나 장애가 끝내 복구되지 않으면 결정적 대체 경로로 내려가고 그 사실을 이벤트로 남긴다. ReRoute의 NIM 어댑터(재시도, `Retry-After`, 텍스트 도구 호출 파싱, `<think>` 분리)와 Retriever 어댑터를 옮겨 온다(본인 저장소).
- 구조화 출력은 `response_format` JSON 스키마로 받는다(Nemotron 3에서 `guided_json` 경로가 거부된 FlyGate 기록).

### 5.3 화면 (Next.js + TypeScript)

1. **승인 대기함** — 실무그룹별 초안. 신뢰도, 근거 수, 크리틱 결과, "검토 필요" 사유.
2. **초안 상세** — 왼쪽 신구조문 비교, 오른쪽 메모 초안. 문장마다 근거 링크, 크리틱이 걸린 문장은 사유와 함께 표시. 아래에 검토 보조 에이전트. 승인 / 수정 후 승인 / 반려(사유 필수).
3. **실행 이력** — 실행 하나를 열면 단계별 시간, 입력·출력 요약, 재시도와 오류, 에이전트 도구 호출 순서, 크리틱 3단 판정, 승인 기록이 시간순으로 이어진다. 각 단계에 **정직성 배지**: NVIDIA 서비스가 실제로 돈 단계는 초록, 대체 구현은 주황, 녹화 재생은 회색 "재현".
   > 2026-11-19: 배지 색은 [디자인 시스템 설계](../../features/design-system/design.md) 2.1절로 바꿨다. 초록과 주황이 품질 판정처럼 읽혀서, 출처 색을 상태 색과 겹치지 않는 보라, 남회색, 점선 회색으로 분리했다.

첫 화면은 데모 안내와 승인 대기함. 로그인 없이 "변호사로 보기 / 관리자로 보기"를 고른다.

### 5.4 배포

지원자 결정: **Render 무료**. 무료 인스턴스는 15분 동안 요청이 없으면 잠들고, 무료 사용 시간이 한 달 750시간이라 서비스 하나만 상시로 깨워 둘 수 있다. 그래서 상시 프로세스가 필요한 것만 Render에 둔다.

| 구성 요소 | 위치 | 이유 |
|---|---|---|
| .NET API + Workflow 엔진 (Docker) | Render 무료 웹 서비스 | `BackgroundService`가 떠 있어야 한다. 외부 상태 확인(UptimeRobot 등, 10분 간격)으로 깨워 둔다 |
| Python AI 서비스 (FastAPI) | Vercel Python 함수 | 상태가 없어 서버리스에 맞는다. 에이전트 상한 120초가 함수 실행 시간 안이다 |
| Next.js 화면 | Vercel | — |
| DB | Supabase Postgres(pgvector) | Render 무료 Postgres는 30일 뒤 만료된다. 매일 수집이 DB를 써서 무료 프로젝트 일시정지도 막는다 |
| 매일 수집, 새벽 초기화 | GitHub Actions 예약 실행 → .NET 엔드포인트 호출(인증 헤더) | Render 무료에는 크론이 없다 |

- 깨우기가 놓쳐 .NET이 잠든 상태로 화면을 열면, 화면은 오류 대신 "서버를 깨우는 중"을 보이고 상태 확인을 반복한다. 실행 상태는 전부 DB에 있으므로 깨어나면 대기 단계부터 이어진다.
- Render 무료 메모리 512MB 안에서 .NET 이미지가 뜨는지 첫 배포 때 확인한다. 넘치면 트리밍·ReadyToRun을 끈 경량 이미지로 줄인다.
- Docker 이미지는 .NET과 Python 모두 만든다(로컬 docker compose로 전체를 한 번에 띄울 수 있게). Vercel 배포는 Python 소스를 직접 올린다.
- GitHub Actions로 테스트, 이미지 빌드, 배포.
- 사내 배포 경로 문서: Nemotron NIM을 법인 GPU에 올리고 `NIM_BASE_URL`만 바꾸는 절차. **실행 검증은 하지 않았다고 명시한다**(ReRoute README의 구분 방식).

## 6. Workflow

한 번의 수집이 개정 건마다 실행 하나를 만든다. 한 실행 안에서 관련 실무그룹마다 `group_review`가 하나씩 생긴다(9절 결정 5).

| 단계 | 하는 일 | 실패 처리 |
|---|---|---|
| 1. 수집 | 기간 내 공포 법령 목록 조회, 원문 저장(수집 시각, 원문 해시) | 네트워크 오류는 지수 백오프 3회. 결과 0건이 사흘 이어지면 이상 신호 알림 |
| 2. 중복 제거 | 법령 ID + 공포일 + 시행일로 멱등 키 | — |
| 3. 조문 확보 | 신구조문 비교 또는 현행·개정 조문 조회. **근거 저장소**에 조문 단위로 저장 | 재시도 3회. 끝내 실패하면 실행 `failed`, 관리자 화면에서 다시 실행 |
| 4. 분류 | Python `/classify`. 그룹별 관련성과 신뢰도 | 429는 재시도 시각 뒤 재시도. 422는 1회 재시도 후 `needs_review` |
| 5. 영향 분석 | 관련 그룹마다 Python `/analyze`. 에이전트가 도구로 찾은 하위법령·판례도 근거 저장소에 추가 | 타임아웃 120초. `insufficient_evidence`면 초안 없이 `needs_review` |
| 6. 크리틱 1단 (.NET) | 인용한 근거 ID가 이 실행의 근거 저장소에 있는가, 문장마다 인용이 있는가 | 없는 인용·인용 없는 문장 표시 → `needs_review` |
| 7. 크리틱 2단 (.NET) | 초안 속 조문번호, 시행일, 공포일, 숫자가 원문과 맞는가 | 불일치 표시 → `needs_review` |
| 8. 크리틱 3단 (Python) | 근거와 숫자는 맞는데 결론이 근거를 넘었는가(과잉해석 규칙) | 걸린 문장과 규칙 ID 표시 → `needs_review` |
| 9. 승인 대기 | 그룹별 담당 변호사에게 배정 | 승인, 수정 후 승인, 반려. 승인자·시각·수정 전후 기록 |
| 10. 알림 | 승인된 그룹의 메모를 데모 알림함으로 발송 | 재시도 3회, 실패하면 관리자 알림. 발송 실패가 승인을 되돌리지 않는다 |

**신뢰도 분기:** 분류 신뢰도 기준 이상은 다음 단계, 중간은 분석하되 `needs_review` 표시, 낮으면 해당 그룹 "관련 없음"으로 닫고 이유를 남긴다.

**상태:** 실행 `queued → running → in_review → completed`(또는 `failed`, `closed_irrelevant`). 그룹 `analyzing → needs_review | waiting_approval → approved → notified`(또는 `rejected`). 실행은 모든 그룹이 끝나면 `completed`이고, 화면은 그룹별 결과를 함께 보여 준다.

## 7. 영향 분석 에이전트

- Nemotron 도구 호출을 직접 루프로 짠다(ReRoute 오케스트레이터 방식). 프레임워크는 쓰지 않는다.
- 도구(전부 읽기 전용): 현행 조문 조회, 신구조문 비교, 관련 하위법령·행정규칙 검색, 판례 검색(국가법령정보센터 범위), 실무그룹 관심사 조회. 검색 도구는 NeMo Retriever 임베딩 + 리랭커로 후보를 고른다.
- 도구가 가져온 문서는 전부 근거 ID(`law:{법령ID}:{조문}`, `prec:{판례ID}` 등)를 받아 근거 저장소에 들어간다. 초안은 그 ID로만 인용할 수 있다.
- 도구 호출 상한 8회, 전체 시간 상한 120초. 넘으면 그때까지의 근거로 `insufficient_evidence`.
- 가드레일(ReRoute 방식): 조문을 확보하기 전에 초안을 쓰려 하면 도구 오류로 되돌려 "먼저 조문을 조회하라"고 안내한다. 모델이 일찍 멈추면 다음 할 일을 최대 2회 안내한다.
- 출력: `{ groups: [{ group, relevance, confidence, reason }], memo: [{ sentence, citations: [근거 ID] }], open_questions: [...] }`. 스키마 검증을 통과해야 반환한다.
- 도구 호출 순서와 각 결과 요약을 응답에 실어 .NET이 저장한다.

검토 보조 에이전트는 조문 조회와 비교 도구만 쓰고, 그 실행의 근거 저장소 밖 질문은 NeMo Guardrails 규칙으로 거절한다. 공개 데모라 IP당 하루 질문 수와 전체 하루 호출 수에 상한을 둔다.

## 8. 크리틱 3단

FlyGate의 크리틱 3단 설계를 법률 도메인에 맞게 새로 구현한다(코드는 옮기지 않고 README에 출처를 밝힌다).

| 단 | 보는 것 | 모델 사용 |
|---|---|---|
| 1단 결정 규칙 (.NET) | 문장마다 인용 존재, 인용 ID가 근거 저장소에 있음 | 쓰지 않는다 |
| 2단 원문 대조 (.NET) | 조문번호, 시행일, 공포일, 기간·금액 숫자가 원문과 일치 | 쓰지 않는다 |
| 3단 과잉해석 판정 (Python) | 근거와 숫자가 맞아도 결론이 근거를 넘었는가 | Nemotron, 여기서만 |

과잉해석 규칙 초안(구현자가 다듬는다):
- 시행일 전 체결된 계약·행위에 적용되는지 경과규정 근거 없이 단정한다.
- 하위법령이 아직 없는 위임 조항을 구체적 의무처럼 쓴다.
- 판례 하나를 일반 원칙처럼 쓴다.
- "반드시", "모든 기업" 같은 범위 확장을 근거 없이 쓴다.
- 벌칙·과태료 금액을 개정 전 조문에서 가져온다.

평가 케이스 세트를 만든다: 과잉해석을 심은 초안과 정상 초안. README에 "규칙 없이 모델만", "규칙 + 모델"의 적발률과 거짓 양성을 수치로 적는다.

## 9. 검토 질문에 대한 결정 (구현자 판단, 승인 시 확정)

1. **입법예고 제외.** 출처가 국민참여입법센터로 다르고 본문이 첨부라 근거 대조가 성립하지 않는다. 공포 법령만 수집하고 입법예고는 향후 계획.
2. **근거 범위는 이 실행의 근거 저장소 전체.** 3단계 조문과 에이전트 도구가 가져온 문서 모두. 저장소에 없는 것은 인용할 수 없다.
3. **공개 데모 상태 관리.** 매일 새벽 데모 데이터를 시드 상태로 초기화한다. 승인은 실제로 동작하되 알림은 외부 Slack이 아니라 화면 안의 "데모 알림함"으로 간다. 검토 채팅은 7절의 상한을 건다. 화면 상단에 "데모 데이터는 매일 초기화됩니다"를 적는다.
4. **실패 분기 시드는 녹화 재생으로 넣고 "재현" 배지를 단다.** 실제 수집 실행과 섞여도 배지로 구분된다.
5. **승인 단위는 그룹.** 6절 상태 참조. 알림도 그룹별.
6. **법령 API 승인 지연 대비.** 승인 전에는 녹화 응답으로 개발한다. 마감 시점까지 신구조문 오퍼레이션 승인이 없으면 현행 조문 두 시점 조회로 대체하고, 그것도 없으면 녹화 데이터 기반 데모로 내고 화면에 밝힌다.
7. **저장소는 공개.** 비밀값은 환경 변수와 시크릿 관리자로만, `.env.example`만 커밋.
