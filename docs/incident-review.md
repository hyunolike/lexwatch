# 장애 회고 규칙

운영에서 사용자에게 보이는 실패(수집 실패, 검토 보조 거절, 배포 뒤 오류)를 고칠 때 쓴다. 고치는 명세(`docs/features/<기능>/spec.md`)의 "해결할 문제" 바로 아래에 아래 표를 둔다. 따로 회고 문서를 만들지 않는다.

근거: Google SRE는 회고 조치를 조사, 지금 피해 줄이기, 부수 피해 복구, 감지, 다음 피해 줄이기, 예방으로 나누고 적어도 피해 줄이기와 예방을 넣으라고 한다([Lunney 외, 2017](https://sre.google/static/pdf/login_spring17_09_lunney.pdf)). 같은 장애가 되풀이되면 처음 회고의 조치가 맞았는지 다시 본다([SRE Workbook](https://sre.google/workbook/postmortem-culture/)). 사람이 아니라 시스템의 원인을 적는다([SRE Book](https://sre.google/sre-book/postmortem-culture/)).

## 표

```markdown
## 회고

- 언제, 무엇이: (UTC 시각, 영향 받은 건수와 화면)
- 언제 알았나: (시각, 누가 어떻게. 발견까지 걸린 시간)
- 같은 장애가 전에 있었나: (있으면 그 명세 링크와 그때 조치가 왜 막지 못했는지)

| 갈래 | 조치 | 상태 |
|---|---|---|
| 지금 복구 | (예: 관리자 재실행) | |
| 감지 | (다음에 더 빨리 알 방법) | |
| 피해 줄이기 | (다음에 나도 영향을 줄일 방법) | |
| 예방 | (다시 나지 않게 할 방법. 없으면 왜 없는지) | |
| 배포 뒤 확인 | (무엇을, 언제. GitHub 이슈 번호) | |
```

## 규칙

- 예방 칸을 비우면 이유를 쓴다. "범위 밖"이면 그 위험을 언제 다시 볼지 적는다.
- 배포 뒤 확인은 `tasks.md`에만 두지 않고 GitHub 이슈(`ops-alert` 또는 `verify` 라벨)로 만들어 확인 뒤 닫는다.
- 예약 작업 실패는 `collect.yml`의 `alert` 작업이 `ops-alert` 이슈로 알린다. 이슈를 닫을 때 원인과 조치를 한 줄 남긴다.
